matsya

Lock files & SBOMs for OS package managers.

Record a machine. Rebuild it anywhere. Know exactly what is in it. matsya snapshots every installed package, with exact versions, hashes and repositories, into a reviewable lock file, replays it on other machines, catches drift, and produces CycloneDX and SPDX SBOMs.

Install ★ Star on GitHub Releases 
$ curl -fsSL https://raw.githubusercontent.com/dmdhrumilmistry/matsya/main/install.sh | sh
$ cargo install matsya
$ matsya lock                 # snapshot this machine into matsya.lock.json
$ matsya sbom -o sbom.cdx.json  # CycloneDX (or --format spdx)
$ matsya check                # exit 1 if anything drifted
$ sudo matsya apply           # rebuild the locked state on another machine

No root needed to install: it uses sudo/doas only when required, otherwise ~/.local/bin; in Termux it installs the native Android build. Every binary ships with a SHA-256 and a GitHub build attestation.

Why matsya

Language ecosystems have had lock files for years. The operating system underneath usually has a hand-written apt-get install line and hope.

🔒

Real lock files

Exact version, architecture, install reason, holds, dependency graph, repository and signing key for every package, plus the SHA-256 from signed repo metadata.

🌍

One file, many machines

Your Mac, the CI runner, the Raspberry Pi and your phone in Termux live side by side as environments in a single lock.

🕰️

Vanished versions still install

Falls back to snapshot.debian.org, snapshot.ubuntu.com, Fedora Koji, the Arch Linux Archive or brew extract, and verifies the hash first.

🧾

Reproducible SBOMs

CycloneDX 1.6 and SPDX 2.3 straight from the lock: purls with distro qualifiers, license expressions, hashes and the dependency graph.

🚨

Drift detection

matsya check exits 1 when a machine no longer matches, including rebuilt packages with the same version but a different hash.

🪶

Depends on nothing

A ~3 MB static binary that reads dpkg, rpm (SQLite, NDB, BerkeleyDB), apk, pacman and Homebrew databases itself. Lock, check and SBOM work with an empty PATH.

How it works

Four commands cover the whole life of a machine.

matsya lock

Reads the package databases directly and writes a deterministic, sorted matsya.lock.json. Re-locking an unchanged machine changes nothing.

matsya sbom

Turns the lock into CycloneDX or SPDX without touching the machine, ready for Grype, Trivy or OSV.

matsya check

Compares the live system with the lock and fails on missing, extra, changed or tampered packages.

matsya apply

Installs the exact locked versions in one transaction with the native package manager, restores install reasons and holds, and verifies archived downloads.

Supported platforms

Every CI run copies the static binary into each distro container and goes through the full cycle: lock, introduce drift, check fails, apply repairs, then rebuild a fresh container from the lock.

Why "matsya"?

In the Matsya Purana, Vishnu takes the form of Matsya, a horned golden fish, and warns the sage Manu of a great flood. Manu fills a boat with the seeds of every plant, every kind of creature and the Vedas, ties it to Matsya's horn, and the fish tows it safely through the deluge. Afterwards, the world is rebuilt from exactly what was saved.

That is the job: record everything a machine is made of, carry it safely, and rebuild the same world somewhere else. In the logo, the cargo is packages.

Documentation

Honest about the limits: Alpine, RHEL clones, openSUSE and Homebrew casks keep no public archive of old versions, and install scripts still run.
